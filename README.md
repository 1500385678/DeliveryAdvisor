## 巡检制度

每个工作日 02:10 由 26-交付-Delivery 顾问自动巡检本仓库,生成 `巡检-交付-YYYYMMDD.md` 落到 `.Log/` 目录。巡检覆盖:

| 维度 | 检查内容 |
|------|---------|
| 阶段 | 当前 Phase(0 骨架 / 1 内容填充 / 2 增强)是否与实际产物一致 |
| 文件 | 文件数 / 代码量 / git status 是否符合阶段预期 |
| 计划 | `.plan/YYYYMMDD.md` 是否落盘(T4 任务是否已写当日计划) |
| 缺口 | 与下一阶段门控的差距(如 Phase 0 → Phase 1 的 T1 主计划 / content/ 章节) |
| 上游 | 同级 `_DeliveryLib/` 10 章节素材是否齐备 |

巡检报告是**只读观察**,不做改动;改动走 T1-T5 任务链路。巡检若发现关键缺口(如 T1 主计划未起草),会在结论中**显式标记"本顾问不应主动代为起草"**,留给张勇决策。

## 开发节奏(cron 双链路)

本仓库由 26-交付-Delivery 顾问**两条自动 cron 任务**维护,职责分明:

| 时间 | 任务 | 触发方式 | 产物 | 性质 |
|------|------|----------|------|------|
| **02:10** | 巡检 | 自动 cron(只读) | `.Log/巡检-交付-YYYYMMDD.md` | **观察**·working tree / phase / 任务清单 |
| **03:10** | 开发 | 自动 cron(本文件) | 1 个小变更(代码/README/配置) | **改动**·读 `.plan/YYYYMMDD.md` 派单 |

**任务命名**(沿用"火车站调度模型 v0.9"·T1-T5 简化):

| 代号 | 动作 | 节奏 |
|------|------|------|
| T1 | 拉 issues / 立项 | 周一 |
| T2 | 改 bug / 写内容 | 周二 |
| T3 | 加 API / 加功能 | 周三 |
| T4 | 优化(文档/结构) | 周四 |
| T5 | 推 release / 自动巡检 | 每日 02:10 + 周五 18:00 |

**`.plan/` 制度**:
- 当日计划由 **T4 在前一天 21:00-22:00** 落盘为 `.plan/YYYYMMDD.md`
- 03:10 cron 读取该计划,执行 1 个小变更,推送双仓
- 完成后**删除**该 plan 临时文件(commit 留存 commit message)
- 若当日 plan 缺失(本顾问自决模式):沿用上一日工作流 + 选最保守的文档/结构增量

**`.Log/` 制度**:
- 02:10 巡检**每天落盘一份**,完整覆盖 working tree / phase / 任务清单状态
- 巡检若发现关键缺口,**显式标记"本顾问不应主动代为起草"**,留给张勇决策
- 巡检是**只读**,不做改动

**双仓推送链路**:
1. `git add -A`
2. `git commit -m "<T代号>: <一句话描述>"`
3. `git push -q -f gitee main`  ← 优先(Gitee 国内快)
4. `git push -q -f github main` ← 备份(允许 30s 超时,失败不阻塞)
5. 推完报告 commit hash + Gitee/GitHub 状态

> 边界:02:10 巡检**不**触发 push;03:10 开发任务**必**推双仓。
